## Phase 3 review round — 4 money-safety blockers found and fixed

Two parallel reviewers audited the implementation: Ai (design) and Yan (finance).
**Yan's audit failed the phase, correctly.** The calculation kernel was sound; the
approval and persistence layers did not actually enforce the guarantees the product
advertises. All four blockers are now fixed and verified.

### The blockers (all confirmed by reading the code, not taken on trust)

**D1 — approval hash check was a tautology.** `approve/route.ts` PUT passed
`resolution.contentHash` as BOTH `approval.contentHash` and `currentContentHash` into
`canExecute()`. So `approval.contentHash !== currentContentHash` compared a value to
itself — always equal, always allowed. The tamper defence was decorative.
Fix: the route now recomputes the hash from live stored content. All three call sites
(propose / approve / execute) go through one shared `proposalHashOf()`.
**Lesson: any hash/token comparison where both sides come from the same variable is
suspect. Grep for `f(x)` and `f(y)` receiving the same argument.**

**D2 — no duplicate-refund prevention across resolutions.** No `refund_key` existed
anywhere. Per-resolution `unique(resolution_id, customer_id)` only stops duplicates
*within one proposal*. A second resolution for the same supplier cancellation could
refund everyone again.
Fix: `refundKey()` = sha256(order | customer | supplier event | cancelled lines),
persisted, plus partial unique indexes `refund_key_executed_uniq` and
`refund_one_executed_per_event`, mirrored in the memory adapter.

**D3 — refund total unbounded.** Only per-row `amount <= paid` was checked. Nothing
capped the batch total at the DB. Now enforced in the atomic write function.

**D4 — non-atomic write.** Resolution then lines as two round-trips: a failed line
insert left an orphaned proposal with a non-zero total and no lines, which could later
be approved and "executed".
Fix: single plpgsql function `write_resolution_atomic()` — commits or rolls back as one
transaction and validates all invariants inside.

**D5 — adapter divergence.** Memory adapter returned silently when already executed;
Supabase threw. Both now throw the same error, so a green test describes production.

**D6 — 32-bit FNV-1a replaced with real SHA-256.** `src/lib/core/sha256.ts` is a
dependency-free implementation verified against Node's `crypto` across padding
boundaries (55/56/63/64/65 bytes) and multibyte UTF-8. A 2^32 digest is collidable,
and a collision would let a different proposal satisfy an approval.

**D7 — float in the money path.** `new-case-screen.tsx` used `(sen / 100).toFixed(2)`
for the editable paid field. Replaced with integer-only `formatMYRPlain()`, asserted to
round-trip through `parseMYR` for all values 0..5000.

**D8 — tie-break now matches spec:** (remainder desc, weight desc, id asc).

### Design findings fixed
- **V1** agent-run step counter could disagree with the screen-reader text by one. Both
  now derive from a single `displayStep` value.
- **V3** drafts had Copy but no Edit, so nothing exercised the edit-invalidates-approval
  loop. Edit added; an unsaved edit blocks approval (`draftDirty`).
- **V5** the disabled-approve reason was not wired to the control. Now `aria-describedby`
  + `role="status"`.

### Design decisions of record
- The message body is deliberately NOT part of the approval content hash (which covers
  only amounts and total). Editing wording must not invalidate an approval of the money.
- Data-integrity refusals throw `IntegrityError` → HTTP **409**, not 500. A client
  seeing 500 would reasonably retry; retrying a duplicate refund is exactly what must
  not happen.
- `scripts/demo-payload.mjs` suffixes the order reference per run. This is required
  because the duplicate guard correctly refuses a second refund for the same event.
  Do not "fix" this by weakening the guard.
- `scripts/verify-approval-gate.sh` is the live HTTP check (17 assertions). It must be
  run against a running dev server; the in-memory store resets on server restart.
